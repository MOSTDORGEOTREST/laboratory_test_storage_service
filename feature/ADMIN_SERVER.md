# Общий админ-сервер: развёртывание лабораторий из админки

Цель: один сервер, на нём N изолированных инстансов LTS (инстанс = лаборатория),
и небольшая админ-панель («control plane»), из которой лаборатории создаются,
останавливаются и обновляются кнопкой — без ручной правки конфигов.

---

## 1. Архитектура

```
                        ┌──────────────────────────────────────────────┐
   *.lts.example.com    │  СЕРВЕР (docker compose)                     │
  ──── DNS wildcard ──▶ │                                              │
                        │  Traefik (реверс-прокси, авто-TLS)           │
                        │    ├─ geo.lts.example.com   → web_geo        │
                        │    ├─ stroy.lts.example.com → web_stroy      │
                        │    └─ admin.lts.example.com → admin-panel    │
                        │                                              │
                        │  admin-panel (FastAPI + Docker API)          │
                        │  web_geo    (image lts:latest, MODE=prod)    │
                        │  web_stroy  (image lts:latest, MODE=prod)    │
                        │  postgres   (ОДИН кластер, база на лабу)     │
                        │  redis      (один, общий)                    │
                        └──────────────────────────────────────────────┘
                                    S3: один бакет, префикс на лабу
```

Ключевые решения:

- **Один Postgres-кластер, база на лабу** (`lab_geo`, `lab_stroy`), а не контейнер
  постгреса на лабу — дешевле по памяти, один бэкап-процесс, один апгрейд.
- **Один Redis** — кеш в приложении фактически не работает (см. memory проекта),
  общий инстанс безопасен.
- **Один S3-бакет**, у каждой лабы свой `S3_PRE_KEY` (`geo/`, `stroy/`) —
  переменная уже есть в конфиге приложения, код менять не нужно.
- **Поддомен на лабу — обязательно.** Кука авторизации называется `Authorization`
  и ставится на весь домен: две лабы на одном домене по путям выбивали бы
  друг друга из сессии. На разных поддоменах куки живут раздельно.
- **Traefik вместо nginx** — чтобы админке не пришлось генерировать и перечитывать
  конфиги прокси: Traefik сам находит новые контейнеры по docker-меткам и сам
  выпускает TLS-сертификаты (wildcard через DNS-01 или по сертификату на поддомен).

## 2. Что делает админка при создании лаборатории

Вход: имя лабы (латиницей, это же поддомен), отображаемое название.

1. **Валидация**: имя уникально, `^[a-z][a-z0-9-]{1,20}$`.
2. **База**: `CREATE DATABASE lab_<name>` в общем кластере
   (+ отдельная роль `lab_<name>` с паролем, права только на свою базу).
3. **Секреты**: сгенерировать `SUPERUSER_NAME`/`SUPERUSER_PASSWORD` (показать
   один раз при создании) и уникальный `JWT_SECRET` (обязательно уникальный:
   общий секрет позволил бы токену одной лабы проходить в другой).
4. **Контейнер**: запустить `web_<name>` из общего образа `lts:latest` через
   Docker API с env и метками Traefik:

   ```yaml
   environment:
     MODE: prod                      # ЖЁСТКО в шаблоне. Никогда не test:
                                     # MODE=test делает drop_all на старте
     DATABASE_URL: postgresql+asyncpg://lab_geo:<pwd>@postgres:5432/lab_geo
     S3_PRE_KEY: geo/
     JWT_SECRET: <уникальный>
     SUPERUSER_NAME: <генерируется>
     SUPERUSER_PASSWORD: <генерируется>
     REDIS_HOST: redis
   labels:
     traefik.enable: "true"
     traefik.http.routers.geo.rule: Host(`geo.lts.example.com`)
     traefik.http.services.geo.loadbalancer.server.port: "8000"
   ```

5. **Реестр**: записать лабу в свою маленькую БД админки
   (name, subdomain, db_name, s3_prefix, status, created_at).
6. **Health-check**: дождаться 200 от `https://<name>.lts.example.com/` и
   показать ссылку + логин/пароль суперюзера.

DNS настраивается один раз: wildcard-запись `*.lts.example.com → IP сервера`.
После этого новые лабы не требуют ни DNS, ни сертификатов, ни правки конфигов.

## 3. Остальные операции админки

- **Стоп/старт** — docker stop/start контейнера лабы.
- **Удаление** — стоп контейнера + финальный `pg_dump` в архив; базу физически
  не дропать сразу (grace-период, например 30 дней).
- **Обновление всех лаб** — `docker pull lts:latest` + поочерёдный пересоздание
  контейнеров (образ один на всех, версии не расползаются).
- **Бэкапы** — cron: `pg_dump` каждой базы + выгрузка в S3 (`backups/<lab>/`);
  админка показывает дату последнего успешного бэкапа по каждой лабе.
- **Мониторинг** — у приложения уже есть `/metrics` (Prometheus); достаточно
  одного Prometheus+Grafana на сервер, target на каждый web-контейнер.

## 4. Безопасность (критично)

- Админка управляет Docker-сокетом — это root-доступ к серверу. Поэтому:
  свой отдельный логин/пароль (не суперюзер лаб), и доступ к
  `admin.lts.example.com` только из офисной сети / по VPN / allowlist IP в Traefik.
- Пароли суперюзеров лаб хранить в реестре только хешированными; сам пароль
  показывается один раз при создании (кнопка «сбросить пароль» = перегенерация
  env + пересоздание контейнера).
- `MODE=prod` зашит в шаблон контейнера и не является полем формы — случайный
  `MODE=test` стирает базу лабы при старте.
- Postgres и Redis не публикуют порты наружу (только внутренняя docker-сеть).

## 5. Порядок внедрения

| Этап | Что | Трудоёмкость |
|---|---|---|
| 0 | Wildcard DNS + Traefik + перевод текущего инстанса на общий compose | ~1 день |
| 1 | Скрипт `create_lab.sh <name>` (те же 6 шагов, но из консоли) | ~1 день |
| 2 | Админка: FastAPI + Docker SDK, таблица лаб, кнопки создать/стоп/обновить | ~3–5 дней |
| 3 | Бэкапы по крону + статус в админке, Prometheus | ~1–2 дня |

Этап 1 даёт 90% ценности сразу: лаба поднимается одной командой, админка на
этапе 2 — это лишь кнопка поверх того же скрипта. UI админки можно собрать в
той же дизайн-системе (style.css уже переносимый).

## 6. Известные ограничения подхода

- Нет сводной аналитики между лабами (базы изолированы) — если понадобится,
  делается отдельным read-only сервисом поверх всех баз кластера.
- Справочник типов испытаний у каждой лабы свой — стоит договориться о едином
  списке, если данные когда-нибудь будут сливаться.
- Номера объектов уникальны внутри лабы; при будущей консолидации баз номера
  между лабами могут совпасть (object_id из EngGeo при этом глобален).
